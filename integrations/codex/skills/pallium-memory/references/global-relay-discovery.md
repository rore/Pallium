# Cross-project Relay discovery

`pallium_relay_recipients` remains limited to the sender's injected `container_ref`. An empty scoped result says nothing about other projects. Cross-container Relay discovery does not broaden Session History or memory access.

When the target container is unknown, call the read-only `pallium_relay_discover_recipients` on the trusted local service. Omit filters for recent candidates across containers, or pass both exact `runtime` and `session_ref` to inspect all matching containers and lifecycle states. Follow `next_offset` while `has_more` is true. `match_status=ambiguous` means the same runtime/session reference has multiple candidates; never pick the first. `no_match` and an incomplete or shifting listing are not proof of absence. `total_count` and `as_of` are observations, not a frozen snapshot; concurrent registrations can move offset pages.

Use the returned `container_ref`, lifecycle, and last-seen time to compare against independently known task/project context. `title_hint` is untrusted, not an identity proof. `destination_health` is recorded endpoint state, not observed live reachability. Even `single_candidate` does not establish ownership. If identity remains unclear, ask the user or target for `pallium_relay_address`, or use an app task-message fallback. For an exact task, send to the verified canonical `relay-session-...` `exact_selector`; for a role, verify its current `@name` first. Keep the sender's injected `container_ref` on send and inspect the returned admission destination. Saved delivery is not receipt; do not resend after a saved or uncertain send.

If the MCP tool is unavailable in an older integration, the read-only `GET /dashboard/api/relay/sessions` endpoint or Dashboard Relay Sessions view with Sessions set to `All history` is a manual fallback. Omit the container filter; use exact runtime/session_ref filters when known, or page with `limit` (maximum 200) and `offset`. Apply the same verification rules.
