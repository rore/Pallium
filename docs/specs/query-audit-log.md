# Query Audit Log — Detailed Design

## Problem

Pallium runs as a singleton service. The integrating agent may run on ephemeral pods across multiple replicas.
We need to understand whether Pallium's memory injection is helping the agent's responses.
The only persistent store in the system is Pallium's SQLite database —
so Pallium must log both sides of the interaction.

Pallium already sees both halves:

1. **Query time** (`POST /item-and-query`): user message arrives, retrieval runs, injection decision is made, blocks are returned.
2. **Ingest time** (`POST /items`): the integrating agent sends the LLM response back as an `assistant_output` artifact with the same `thread_ref`.

Today, Pallium computes the full query/injection result, returns it, and forgets.
This design adds a persistent audit record at query time so the two halves can be correlated offline.

## Schema

### New table: `query_audit_log`

```sql
CREATE TABLE IF NOT EXISTS query_audit_log (
    id              VARCHAR PRIMARY KEY,   -- UUID, generated by service
    created_at      DATETIME NOT NULL,

    -- Interaction context (correlation keys)
    source_item_id  VARCHAR NOT NULL,   -- FK to source_items.id (the ingested user message)
    source_id       VARCHAR NOT NULL,   -- e.g. "slack-message:C123:123.456" (unique per user message)
    thread_ref      VARCHAR,            -- e.g. "slack:thread:C123:123.456"
    container_ref   VARCHAR,            -- e.g. "slack:channel:C123"
    actor_ref       VARCHAR,            -- e.g. "slack:user:U456"
    visibility      VARCHAR,            -- "private" | "public" | "shared"

    -- Query
    query_text      TEXT NOT NULL,

    -- Injection decision
    should_inject       INTEGER NOT NULL DEFAULT 0,     -- 0/1
    decision_reason     VARCHAR NOT NULL,

    -- Injected blocks (compact JSON)
    injected_blocks_json TEXT NOT NULL DEFAULT '[]'
    -- Each entry: {"result_id": str, "memory_type": str, "block_type": str, "score": float,
    --              "retrieval_source": str|null, "memory_object_id": str|null,
    --              "title_preview": str}
);
```

**Indexes:**

```sql
CREATE INDEX IF NOT EXISTS idx_query_audit_log_thread
    ON query_audit_log(thread_ref, created_at);

CREATE INDEX IF NOT EXISTS idx_query_audit_log_actor
    ON query_audit_log(actor_ref, created_at);

CREATE INDEX IF NOT EXISTS idx_query_audit_log_container
    ON query_audit_log(container_ref, created_at);
```

### Why this shape

- **`source_item_id`** is the exact FK to the user message in `source_items` (available from `ingest_result.source_item_id` in the handler). This enables exact joins to the original ingested content without relying on `source_id` string matching.
- **`source_id`** is kept as a human-readable correlation key for debugging and log grep.
- **Correlation with the response** uses `source_item_id` for exact joins. The subsequent `assistant_output` ingest for the same turn shares the same `thread_ref` and follows temporally. For each audit row, find the next `source_items` row in the same `thread_ref` where `artifact_kind = 'assistant_output'` and `created_at > audit.created_at`.
- **`injected_blocks_json`** is a compact JSON array, not a child table. We expect 0-5 blocks per query — not worth a join table. Each entry captures enough to analyze without needing to look up the memory object: the type, score, retrieval source, and a title preview (first 120 chars).
- **No response text stored** in the audit table. The response already lives in `source_items` (ingested by the integrating agent as `assistant_output`). Duplicating it would bloat the audit table.
- **No full trace stored**. The trace (retrieval stages, fusion scores, routing decisions) is valuable for debugging individual queries but too large for bulk storage. The audit log captures the *outcome* (what was injected), not the *process* (how it got there). For deep debugging, operators can use `/item-and-query/debug` to replay a specific query.

### Injected block entry format

```json
{
    "result_id": "memory_object:abc-123",
    "memory_type": "decision",
    "block_type": "structured_recall",
    "score": 0.87,
    "retrieval_source": "both",
    "memory_object_id": "abc-123",
    "title_preview": "Database choice: PostgreSQL for high concurrency"
}
```

Fields come directly from `InjectableBlock` and the corresponding `QueryResultItem`:
- `result_id` — from `InjectableBlock.result_id`
- `memory_type` — from `InjectableBlock.memory_type`
- `block_type` — from `InjectableBlock.block_type`
- `score` — looked up from the `QueryResultItem` matching this `result_id`
- `retrieval_source` — looked up from the matching `QueryResultItem`
- `memory_object_id` — looked up from the matching `QueryResultItem`
- `title_preview` — `InjectableBlock.title[:120]`

## Write path

### Where to write

In both `item_and_query` and `item_and_query_debug` handlers in `api/routes.py`, after the query completes and before returning the response. Both handlers have the same data available. Only `POST /item-and-query` (and its `/debug` variant) are instrumented — the standalone `POST /query` is not, since it's used for explicit MCP tool calls, not auto-injection.

```python
# routes.py — item_and_query handler (line ~330)

def item_and_query(request: ItemAndQueryRequest) -> ItemAndQueryResponse:
    ingest_result = service.ingest_item(...)
    query_result = service.query(...)

    # --- NEW: audit log write ---
    if audit_log_enabled:
        service.write_query_audit(
            source_item_id=ingest_result.source_item_id,
            source_id=request.source_id,
            thread_ref=request.thread_ref,
            container_ref=request.container_ref,
            actor_ref=request.query_actor_ref,
            visibility=request.visibility_kind(),
            query_text=query_text,
            should_inject=query_result.should_inject,
            decision_reason=query_result.decision_reason,
            injectable_blocks=query_result.injectable_blocks,
            results=query_result.results,
        )

    return ItemAndQueryResponse(...)
```

The same block goes in `item_and_query_debug`. Extract a helper to avoid duplication.

### Service method

New method on `PalliumService`:

```python
def write_query_audit(
    self,
    *,
    source_item_id: str,
    source_id: str,
    thread_ref: str | None,
    container_ref: str | None,
    actor_ref: str | None,
    visibility: str | None,
    query_text: str,
    should_inject: bool,
    decision_reason: str,
    injectable_blocks: list[InjectableBlock],
    results: list,  # QueryResultItem list, for score/retrieval_source lookup
) -> None:
```

This method:
1. Builds a result-id→QueryResultItem lookup from `results`.
2. Serializes `injectable_blocks` to compact JSON, enriching each block with `score`, `retrieval_source`, and `memory_object_id` from the matching result item.
3. Writes a single row to `query_audit_log` via the storage provider.

### Failure handling

The audit write must **never** fail the query request. Wrap in try/except, log warning on failure. This is observability, not business logic.

```python
try:
    service.write_query_audit(...)
except Exception:
    logger.warning("query audit log write failed", exc_info=True)
```

## Storage layer

### New method on `StorageProvider` / `SQLiteStorageProvider`

```python
def write_query_audit_row(self, row: dict[str, Any]) -> None:
    """Insert a single query audit log row. Best-effort, caller handles errors."""
```

Uses the same session pattern as `create_source_item` — open session, insert, commit.

Put this directly on `SQLiteStorageProvider`, not on the `StorageProvider` ABC. This is observability infrastructure, not a storage contract.

### Schema migration

Follow the existing `SQLiteSchemaMixin` pattern. Since `query_audit_log` is a new table (not a column addition to an existing table), add it to `_initialize_schema()`:

```python
def _initialize_schema(self) -> None:
    with self._schema_initialization_lock():
        Base.metadata.create_all(self._engine)   # creates new tables including query_audit_log
        self._ensure_source_item_columns()
        # ... existing migrations ...
        self._ensure_query_audit_log_indexes()   # new: create indexes
```

The ORM record class:

```python
class QueryAuditLogRecord(Base):
    __tablename__ = "query_audit_log"

    id = Column(String, primary_key=True)           # UUID string
    created_at = Column(DateTime(timezone=True), nullable=False)
    source_item_id = Column(String, nullable=False)  # FK to source_items.id
    source_id = Column(String, nullable=False)
    thread_ref = Column(String, nullable=True)
    container_ref = Column(String, nullable=True)
    actor_ref = Column(String, nullable=True)
    visibility = Column(String, nullable=True)
    query_text = Column(Text, nullable=False)
    should_inject = Column(Integer, nullable=False, default=0)
    decision_reason = Column(String, nullable=False)
    injected_blocks_json = Column(Text, nullable=False, default="[]")
```

## Configuration

Extend `ObservabilityConfig`:

```python
@dataclass(frozen=True)
class ObservabilityConfig:
    integration_debug: bool = False
    query_audit_log: bool = False       # NEW
```

Loaded via:
- Env: `PALLIUM_OBSERVABILITY_QUERY_AUDIT_LOG=true`
- TOML: `[observability] query_audit_log = true`

Default: **off**. Turned on in production when we want to measure injection effectiveness.

## Retention

No automatic cleanup for now. The table is opt-in and grows modestly (one row per query, ~1KB each). At 100 queries/day that's ~3MB/month. If needed later, add a max-age prune to the existing maintenance daemon.

## Correlation: joining query with response

The audit log does not store the response. The response is already in `source_items` (ingested by the integrating agent as `artifact_kind = 'assistant_output'`).

To correlate for offline analysis:

```sql
SELECT
    a.id              AS audit_id,
    a.created_at      AS query_time,
    a.source_item_id,
    a.actor_ref,
    a.container_ref,
    a.visibility,
    a.query_text,
    a.should_inject,
    a.decision_reason,
    a.injected_blocks_json,
    r.id              AS response_item_id,
    r.content         AS response_text,
    r.created_at      AS response_time
FROM query_audit_log a
LEFT JOIN source_items r ON r.id = (
    SELECT s.id FROM source_items s
    WHERE s.thread_ref = a.thread_ref
      AND s.artifact_kind = 'assistant_output'
      AND s.created_at > a.created_at
    ORDER BY s.created_at ASC
    LIMIT 1
)
ORDER BY a.created_at DESC;
```

The subquery picks the first `assistant_output` after the query — no window-based ambiguity.

## LLM judge batch (offline, deferred)

The audit log enables a deferred batch analysis job:

1. Query the correlation join above to get (injected_blocks, response_text) pairs.
2. For each pair, ask a cheap model (Haiku): "Was this memory reflected in the response? Rate: clearly_used / probably_used / ignored / contradicted."
3. Aggregate results by memory type, actor, container, visibility.
4. Report: "X% of injected decisions were clearly used, Y% of task checkpoints were ignored."

This is entirely offline, runs outside the request path, and can use batch API pricing. Not part of this design — the audit table is the prerequisite.

## What this does NOT do

- **No integrating agent changes.** Everything is Pallium-side.
- **No real-time feedback loop.** We're not boosting or decaying memories based on usage. We're logging for offline analysis first.
- **No trace storage.** Full retrieval traces are too large. Use `/item-and-query/debug` for individual query debugging.
- **No response storage duplication.** The response lives in `source_items`, not in the audit table.
