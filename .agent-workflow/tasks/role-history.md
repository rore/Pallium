**Outcome:**
Successor sessions can recover and search eligible source history by exact Relay name, with every source item in a turn attributed to the validated name held when that turn began.

**Target:**
Pallium Relay and Session History.

**Scope:**
Implement exact turn-start Relay-name attribution and exact-name Session History search across supported capture surfaces; update the API/MCP contract, focused E2E coverage, maintained Pallium guidance, and canonical roadmap item.

**Constraints:**
Capture the Relay name validated at turn start for the whole turn, including delayed assistant capture and retries; unavailable, confirmed unnamed, and legacy unknown remain distinct. Exact-name filtering runs before result ranking and retains existing scope, visibility, redaction, deletion, and lookup provenance. No role registry, guessed backfill, access expansion, runtime/install/config/dependency changes, or edits to the source-lifetime bridge owner’s file.

**Completion criteria:**
When session A records a turn under Relay name N and session B later takes N through existing authorization, B's exact-name history search returns eligible source items from both sessions with original session and lookup provenance. A later turn from A is not attributed to N. Old rows remain unknown; missing capture is reported as incomplete, and exact search cannot expose out-of-scope or forgotten sources. Supported host integrations preserve the turn-start attribution across delayed capture/retries, verified by public-surface E2E tests.

**Discovery:**
At verified main `5d1679364d8404601b0be14216746d2b8fe2f286`, `pallium_relay_address` in `app/mcp/server.py` validates the integration's runtime/session against the current Relay endpoint and returns an optional `alias_selector`; a valid response without it means confirmed unnamed, while an error or invalid/missing identity is unavailable. `storage/sqlite_relay.py` already includes the current `alias` in the `relay_turn` session view and clears the former holder on takeover; it stores only current ownership, not binding history. Codex and Claude turn-start hooks call `relay_turn`, but their injected text omits the alias. Claude's `pre_compact` hook does not call Relay; Codex has no pre-compact hook. Hermes exposes both address and history tools through its plugin, with no promise of host-managed compaction refresh.

History is `pallium_search_history` (`app/mcp/server.py`) → `POST /query` (`api/routes.py`, `api/schemas.py`) → `PalliumService.query` and the `source_only` retrieval path. Material design constraint: source-time name must travel with the turn context captured before delayed assistant ingestion. Adding a history filter alone is insufficient. **Material assumptions:**

Official Codex Hooks documentation (`https://developers.openai.com/codex/hooks`, UserPromptSubmit and Stop payload sections) documents the same native opaque `turn_id` on both events. A supported Codex payload can use that exact key, constrained by `source_type`, `container_ref`, `thread_ref`, and user role, to resolve the retained user row for delayed assistant capture. Enforce one user snapshot per composite key with a scoped unique index: a repeated UserPromptSubmit with the same Relay state/name reuses the original row; a conflicting state/name never overwrites it and fails closed. Treat the key as correlation data only, never authority. The existing `/items` route has no caller authentication, so do not describe client-supplied start attribution as cryptographically trusted; bind it only to the existing local integration/source identity and authorization scope, ignore all assistant-supplied attribution, and document this boundary.
