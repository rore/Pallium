Existing read surface: add GET /dashboard/api/relay/operational-preview beside existing Relay reads in app/dashboard.py. This avoids changing the payload-bearing messages response or API/MCP/storage layers. This is an operator metadata preview supporting retention planning; it neither proposes eligible deletion candidates nor clears the eight durable pending deliveries.

Inputs: limit default 50, accepted 1..200; until UTC datetime optional first page; before_created_at and before_id (delivery ID) supplied together; trace_through_sequence optional first page, integer 0..2^63-1. A continuation requires original until and trace_through_sequence, and the returned cursor pair. Optional runtime (recipient runtime enum) and container_ref (admission message container) filters remain exact and fixed throughout a scan. Reject malformed bounds/cursor pairs, future until, sequence above the database high-water, and continuation cursors outside until with 422. Unknown exact filter matches return an empty page. Unsupported backend returns existing dashboard-style 501. No caller-supplied file paths, raw SQL, native locations, or baseline blobs.

Pagination: one row per delivery, ordered by message.created_at descending then delivery.id descending, limit+1 selection and returned cursor. Fixed until bounds creation time; first page captures trace_through_sequence from the immutable trace PK. Read metadata and trace boundary within a real single SQLite read transaction per response (do not mistake SQLAlchemy implicit begin for the SQLite legacy driver's actual transaction). Subsequent pages reuse these boundaries. Rows created after until are excluded; backdated administrative inserts, deletion/pruning, or restored databases can change membership and must not be described as a frozen snapshot. Mutable delivery/session/reservation state, effective expiry, lease expiry and recipient recency are evaluated at each response's observed_at, not membership until. Response labels consistency as creation-cutoff/trace-highwater/live-state, never a frozen historical snapshot. Uncertain continuity remains unknown.

Output allowlist per row: delivery_id, message_id, created_at; sender_endpoint_id and recipient_endpoint_id; recipient_runtime; admission container_ref; stored_state and effective_state; durable flag and public expires_at (null for durable); claimed_at, lease_expires_at and lease_state (not_claimed/active/expired/unknown); delivered_at; recipient stored state, last_seen_at, and recency (recent/dormant/unknown), with closed state separate from recency; Codex reservation outcome or absent, explicitly not native-runtime liveness; in_reply_to, parent existence and linked-reply count; latest bounded trace sequence/time/stage and latest completed trace sequence/time/outcome, plus stored trace_version/pruned/truncated and explicit missing or uncompleted-trace/attempt-status-unknown evidence. A prepared/associated event without completion never establishes an attempt is still running; trace writes are best-effort. Stored flags do not prove the whole trace is complete. No recursive chain expansion, free-text reason, arbitrary evidence_json, session/native reference, title, alias, receipt, claim_token, payload/preview or payload hash. Trace reason is deliberately excluded because source accepts bounded redacted free text, not solely enum codes. A missing row/recipient/parent or unknown enum yields explicit unknown evidence, not success/failure inference. Do not consult or mutate native runtime hosts.

Top-level: items, limit, has_more, next_before_created_at/id, until, observed_at, trace_through_sequence, and consistency/evidence notes. Avoid global total/count scans; existing summary owns aggregate totals. Scalar projections select only allowlisted columns. Trace/reply/reservation queries are scoped to at most the returned page's IDs; no N+1 query per row and no loading full ORM entities. Use correlated EXISTS/count or a grouped bounded-page query for graph facts. Preserve dangling-parent evidence; never fix it during read. The 200-row guarantee bounds response/materialization, not SQLite scan/sort work: created_at and in_reply_to are not indexed in the current schema, and this slice adds no indexes. Filter consistency is caller discipline because filters are not cryptographically bound into existing timestamp/ID cursor conventions; save exact filters with the baseline and reset on change.

Baseline use belongs to the caller, with no new storage: save complete scan IDs/states and trace boundary plus fixed filters. Unchanged old pending identities remain historical backlog. New IDs are newly observed deliveries; new latest failure evidence above the previous trace boundary is a separate evidence change, not proof every deferred attempt is an active incident. An observed old ID transitioning to delivered/expired/suppressed is a terminal-state change; delivery does not imply reply or task completion. Missing IDs, filtered-out rows, incomplete scans, trace pruning, or absent evidence are unknown, never automatic resolution. A latest successful outcome or terminal delivered state prevents an old failure record from being presented as a current new failure. Changing filters resets the comparison baseline. The endpoint provides evidence only; alert thresholds and scheduling are not part of this slice.

Future destructive cleanup still depends on separately accepted windows, send/reply idempotence after pruning, late-reply semantics, reply-graph preservation, claimed/durable/wake fences, candidate-preview/apply drift rejection, atomic deletion, backup/rollback, and explicit live rollout approval.
