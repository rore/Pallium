**Outcome:**
Operators can inspect a bounded, non-secret, end-to-end evidence trail for one Relay delivery across persistence, activation, admission, and terminal delivery state without changing delivery correctness.

**Target:**
Pallium.

**Scope:**
Relay delivery-trace persistence and retention, shared correlation/projection semantics, HTTP and MCP read surfaces, dashboard presentation, focused lifecycle/E2E coverage, and the owning roadmap/docs.

**Constraints:**
Reuse the existing Relay store and cleaner; one shared projection must feed HTTP/MCP/dashboard; diagnostic writes are best-effort and can never fail, retry, or mutate delivery behavior; expose no payload text, secrets, claim tokens, receipts, or raw provider output; coordinate shared outcome vocabulary with `@pall-arc`; do not edit the prerequisite activation-contract worktree or merge/restart before coordination.

**Completion criteria:**
For any Relay delivery, the supported read surfaces shall show the same bounded, ordered evidence with explicit correlation, coalescing, retention/pruning, legacy-gap, and uncertain-outcome semantics; missing or failed diagnostics shall be visible as absence/gaps and shall not affect the delivery lifecycle; all observable edge cases shall have caller-surface E2E coverage.

**Risk:**

**Complexity:**

**Discovery:**
Current main has one authoritative Relay message/delivery store. `RelayDeliveryRecord.attempts` counts receiver claims, not native activation attempts; current claim, lease, delivery, expiry, immutable send-time endpoint, and endpoint-generation state already supply the authoritative lifecycle facts. `app/dependencies.py` is the single wake composition seam, while `app/codex_wake.py` and `app/claude_wake.py` own native submission/coalescing and emit only logs or correctness-registry state. Codex keeps an in-process per-session generation and suppresses duplicate queued writes until admission; Claude persists an exact-session `wake_inflight` generation and delivery ID. Neither provides a common queryable attempt ledger. Existing query-audit, historical-reuse, metrics, and promotion-event tables have unrelated authority, fields, retention, and privacy contracts, so reusing them would create a second interpretation rather than reuse a Relay facility. The dashboard already exposes message detail and immutable delivery targets; MCP status already has bounded output handling; the existing cleaner owns maintenance but is disabled by default. Local read-only traffic on 2026-09-12 showed 1,499 retained messages, 113 in the latest day, 609 in seven days, and 1,499 in thirty days. The prerequisite `feat/relay-activation-contract` Work Record at `1af2f535` proposes `accepted|deferred|uncertain|failed`, keeps admission separate, and explicitly excludes persistence. Coordination with `@pall-arc` confirmed the compatibility boundary: activation owns the proposed vocabulary, truthful adapter mapping, and read-only capability projection after its own approval; trace owns durable activation-attempt identity, immutable stages, one-to-many delivery association, and readback. There is no suitable stable attempt identifier today: delivery IDs are per delivery, Codex generation is process-local, and Claude generation is fencing state. Trace must mint the ID before adapter invocation; endpoint `scope_generation` is audit/fence context only.

**Material assumptions:**
- Wait for and rebase on the prerequisite activation-contract change, then import its canonical `ActivationAttemptResult` and activation projection names; this task will not freeze the proposed names early, define parallel enums, or edit the prerequisite worktree. The proposed result fields are outcome, bounded/redacted reason, bounded evidence, native-retry safety, and optional proven destination-health update; `uncertain` is never native-retry-safe.
- The smallest viable persistence is one immutable stage-event row per `(attempt_id, delivery_id, stage)` in the existing Relay SQLite database. Initial stages are `prepared`, `associated`, and `completed`; outcomes exist only on completed events. Coalesced deliveries share one `attempt_id`; association rows do not invent attempts. Each row gets its own recorded sequence, so late completion cannot mutate an earlier page. Do not ship a `resolved` stage unless the merged prerequisite exposes a real authoritative late-result producer; ACK/admission is not that producer.
- Existing delivery columns remain authoritative for immutable send-time target, current claim/lease/delivery/expiry state, and the cumulative receiver-claim count. The projection may report that multiple claims imply recovery, but it cannot fabricate timestamps or order for overwritten historical claims. Current lifecycle state is a separately labeled live snapshot outside the frozen diagnostic-event page.
- Diagnostic completeness is always `best_effort`. A nullable trace version distinguishes pre-feature legacy rows; delivery flags disclose known per-delivery truncation or retention pruning. An unmarked partial write failure remains explicitly possible and is never presented as complete evidence.
- Retained evidence is capped at eight activation attempts / twenty-four stage events per delivery and sixty-four delivery associations per attempt; pruning permits later evidence, so these are not lifetime recording limits. Retention is thirty days with 100,000 total stage rows. At the latest observed day, eight attempts with three stage rows each would be about 81,360 rows in thirty days; ordinary one-attempt traffic is about 10,170 rows. The existing cleaner process runs trace cleanup even when memory retention is disabled. The insert path never prunes: at either association or global capacity it drops the new diagnostic fact and best-effort marks that delivery truncated. The cleaner frees age/cap space in transactions of at most sixty-four rows, marking only bounded then-known associates pruned; a later/unrecorded associate remains honestly `best_effort/unknown`. Delivery state and native-write behavior never depend on this path.
- Operational code never waits for diagnostic persistence. A bounded one-thread executor with sixty-four nonblocking slots follows the existing usage-audit handoff pattern: callbacks only acquire a slot without waiting and submit an immutable fact; full/closed queues drop it. The worker uses a diagnostic-only SQLite connection/session with a 25 ms maximum lock wait and no ordinary retry wrapper; 25 ms bounds lock acquisition, not total callback or I/O duration, and the correctness path keeps its existing timeout/retry settings. No enqueue or database call occurs while an adapter coalescing/capability lock is held. Reads use a nonmutating Relay query rather than `relay_message_status`, whose current implementation expires rows as a write side effect.
- Each shared `schedule_codex_relay_wake` / `schedule_claude_relay_wake` entry mints a fresh opaque `activation_attempt_id` when it creates a new reservation, covering send, ACK rearm, and recovery callers. A later delivery either adopts an existing live reservation ID and emits `associated` after the scheduler lock is released, or gets a distinct evaluation/attempt ID. Completion is stored once for the owning delivery; readback follows the attempt ID to shared stages so every already-associated delivery sees the same outcome. Completion-before-association and association-before-completion are both valid.
- Reservation limitations remain explicit. Codex retains the diagnostic ID for its existing queued/ambiguous reservation until admission. Claude's worker-local reservation ends after transport while its correctness registry may remain `wake_inflight`; a later scheduling evaluation in that window is `deferred/attempt_inflight` with a new evaluation ID and no claimed association to the earlier attempt. After restart, lost process-local correlation is unknown; mint a new ID only for an actually new native submission. Never persist diagnostic identity into correctness state or imply continuity from generation/timestamps.
- If the merged prerequisite does not expose the normalized result at these scheduler/worker orchestration points, stop and return to design; timestamp/hash inference is not acceptable.

**Verification plan:**
When one native activation serves one or many deliveries, each HTTP/MCP/dashboard read follows the same bounded attempt ID to shared completion evidence without incrementing the receiver-claim counter; unsupported Claude lifetime/restart correlation stays deferred or unknown -> controlled send/rearm/direct-recovery Codex/Claude E2E and cross-surface exact projection assertions.
When an attempt is prepared, deferred, accepted, uncertain, failed, or completed later, the projection preserves stable recorded sequence and explicit stage relationships despite timestamp ties/rollback; it never claims recorded order is causal or equates acceptance with admission -> fault-injected adapter and restart E2E.
When a natural turn claims, recovers a lease, ACKs/replies, or expires, the trace shows only the current authoritative snapshot and cumulative claim count, labels prior claim chronology unavailable, and remains read-only -> three-claim/two-recovery HTTP/MCP/hook E2E with clock rollback and state/native-call counters.
When writes, reads, or cleanup fail or exceed 25 ms lock wait, the original send/wake/coalescing/claim/ACK result, lease handling, and native-write count remain unchanged; evidence stays explicitly best-effort and known gaps are disclosed when their marker persisted -> contention, partial-loss/restart, and injected failure tests through caller surfaces.
When per-delivery, per-attempt association, age, or global bounds apply, the operational path drops diagnostics without pruning; an immutable-event upper bound excludes later appends but may disclose cleaner-pruned rows between pages; cleanup uses at most sixty-four rows per transaction even during high-fanout coalescing and concurrent ACK, and separate Relay DBs leave no trace orphans -> boundary and retention E2E.
When inputs are unknown, legacy, malformed, Unicode, redacted, aliased, transferred, closed, reactivated, or concurrently appended, all three surfaces return the same bounded contract with no payload/secrets/raw provider data -> public API/MCP/dashboard E2E.
