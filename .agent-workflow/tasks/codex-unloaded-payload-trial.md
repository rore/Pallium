## Proposed security correction pending task-owner acceptance

Before the operator creates the test delivery, the service installs one protected, durable, create-once trial marker for one exact endpoint/session/container and immutable trial action key. Installation and the Codex dispatch guard plus reservation run under the same app-level lock, including a deterministic concurrent callback test. The installer verifies no existing native reservation or in-flight launch; an accepted or uncertain older reservation aborts this trial, never gets cleared. `dispatch_relay_wake` consults the marker at the single Codex branch used by both send callbacks and `recover_expired_relay_wakes`, and denies native scheduling for that endpoint while it exists. A failed/ambiguous marker read denies native launch for this exact enrolled trial, rather than silently reverting to native. The operator then creates one durable pending message; a separate create-once binding records its exact delivery ID before action. The service requires that binding, current pending/scope readback, positive inventory lifetime proof, current peer/finite authority, and no prior spent action fence. It atomically spends the immutable endpoint/trial key before one fixed native owner call. The spent fence remains after revoke, cleanup, service restart, epoch/revision change, and a later delivery to that endpoint. No later ticket for the endpoint may authorize another owner action under this finite experiment. Never create a fake accepted native reservation or infer suppression from the one-second delay. Missing positive source exit within the finite 180-second window ends the trial without archive, forced exit or blind repeat.

This correction adds `app/dependencies.py` (the shared send/recovery native dispatch branch) and its caller tests to prospective code scope. It also requires a concrete red send-path plus recovery-path test proving no native launch while the marker is active, then one retained-service owner call maximum; later delivery, restart and rearm must remain fenced. All owner outcomes/logs are fixed enums only, with no raw native response, arguments, schema, endpoint, capability or payload. The exact installed Desktop `tools/call` schema remains a pre-edit prerequisite, proven by a decoded fake-pipe request.
